# 2. PRODUCT DEFINITION: WHAT TANAT ACTUALLY IS

Tanat is an AI infrastructure platform that enables businesses to provision, configure, manage, and deploy intelligent AI agents across their business operations and existing digital channels.

The fundamental problem Tanat solves is this:

Businesses increasingly need AI to handle different operational responsibilities, but building production-ready AI agents requires technical expertise, model integrations, orchestration, memory, knowledge retrieval, tool integrations, permissions, security, and ongoing infrastructure management.

Most businesses should not have to build all of this themselves.

Tanat provides that infrastructure.

A business should be able to:

1. Create an account.
2. Register its business and establish its workspace (tenant).
3. Describe its business, industry, products, services, and operations.
4. Identify the responsibilities it wants AI agents to handle.
5. Provision agents for those responsibilities.
6. Configure each agent's knowledge, behaviour, tools, permissions, and workflows.
7. Connect the agent to the channels and business systems it already uses.
8. Test the agent.
9. Deploy it.
10. Monitor its activity, performance, usage, and costs.

The business should not need to understand model orchestration, vector databases, inference infrastructure, agent execution engines, or the complexity of building AI systems.

Tanat handles the underlying infrastructure.

### Core positioning

**Tanat is the AI infrastructure behind your business operations.**

Supporting positioning:

"Provision intelligent AI agents for your business, connect them to your tools, and deploy them wherever your customers and teams work. Tanat handles the intelligence and infrastructure behind them."

Alternative messaging:

- AI agents for every part of your business.
- Your business needs AI. Tanat provides the infrastructure.
- From business knowledge to deployed AI agents.
- Configure once. Deploy across your business.
- Give your business an AI workforce without building AI from scratch.

Do not position Tanat exclusively as:
- An AI chatbot builder.
- An AI sales assistant.
- A payment processing platform.
- An e-commerce AI tool.
- A WhatsApp bot generator.
- A generic AI wrapper.

Those are either possible use cases or individual capabilities, not the entire product.

# 4. THE FUNDAMENTAL TANAT ARCHITECTURE

Use the following conceptual model throughout the application.

## A. Tenant / Business Workspace

A tenant represents a business organisation or workspace.

A tenant is NOT necessarily a single domain.

One tenant may have:
- Multiple business users.
- Multiple domains.
- Multiple brands.
- Multiple AI agents.
- Multiple integrations.
- Multiple deployments.
- Different business environments.

Tenant-level resources and data must be isolated.

The business owner or workspace administrator manages the tenant.

## B. Agents

A tenant can create and manage multiple agents.

Examples:

- Customer Support Agent
- Sales Agent
- HR Assistant
- Booking Agent
- Operations Assistant

Each agent has its own configuration, knowledge access, permissions, integrations, and deployment settings.

## C. Agent configuration

Each agent should have a structured configuration consisting of:

- Name.
- Description.
- Purpose.
- Agent category.
- Instructions and behaviour.
- Personality and communication tone.
- Model configuration.
- Knowledge sources.
- Memory configuration.
- Available tools.
- Permissions.
- Connected systems.
- Workflows.
- Escalation rules.
- Usage limits.
- Version information.
- Deployment status.

Avoid presenting all these technical settings to a new user immediately.

Use progressive disclosure: simple setup first, advanced configuration when needed.

## D. Channels and deployments

An agent's intelligence should be independent of the channel where it operates.

The same configured agent should be deployable to multiple channels.

For example, one Customer Support Agent can operate on:

- Website widget.
- WhatsApp.
- Telegram.
- Slack.
- Email.
- A custom application through the API.

The agent should not need to be recreated for each channel.

Channels are interfaces and delivery mechanisms connected to the same underlying agent configuration.

Support channel-specific capabilities where necessary, without creating separate agent brains.

## E. Business system integrations

Separate communication channels from business-system integrations.

Communication channels include:
- Website.
- WhatsApp.
- Telegram.
- Slack.
- Email.
- Other supported messaging interfaces.

Business-system integrations include:
- Shopify.
- CRM systems.
- Calendars.
- Payment providers.
- Inventory systems.
- Accounting software.
- Internal APIs.
- Databases.
- Project management tools.

A business may connect a communication channel and multiple business systems to one agent.

## F. Tanat infrastructure

Tanat owns the underlying AI infrastructure:

- AI inference.
- Agent orchestration.
- Knowledge retrieval.
- Memory.
- Tool execution.
- Workflow execution.
- Tenant isolation.
- Credential management.
- Permissions and approvals.
- Conversation management.
- Logging and observability.
- Usage metering.
- Billing.
- APIs and SDKs.

The business interacts with a simple product experience while Tanat manages the complexity.

# 5. EXISTING IMPLEMENTATION: IMPORTANT CONSTRAINTS

The existing application already has:

1. NEAR AI Cloud integration.
2. OTP-based authentication.

These have already been wired into the project.

**Do not rebuild these features from scratch.**

First inspect their implementation.

### NEAR AI Cloud

- Identify how inference is currently connected.
- Understand the existing API configuration.
- Identify existing model invocation and response handling.
- Preserve working credentials and environment-variable conventions.
- Identify how agents will use the existing inference integration.
- Build the required agent orchestration and business functionality around it.
- Keep inference provider logic modular so other providers can be added in the future.

NEAR AI Cloud is the current inference foundation, not the entire Tanat product.

Do not assume it already provides Tanat's tenant management, knowledge management, connector infrastructure, agent lifecycle, or business workflows.

Implement those responsibilities at the Tanat application level where required.

### OTP authentication

- Preserve the existing OTP sign-in experience.
- Inspect the authentication implementation before changing anything.
- Ensure the authenticated user is associated with a tenant/workspace.
- Support invitations and membership in multiple workspaces if the existing architecture permits.
- Do not unnecessarily introduce passwords or another authentication system.

### General preservation requirements

- Inspect the repository before making architectural changes.
- Identify existing pages, routes, APIs, database models, and reusable components.
- Reuse existing functionality wherever possible.
- Do not replace working implementations simply because you prefer another library.
- Do not introduce unnecessary dependencies.
- Keep existing environment variables secure.
- Never expose API keys or provider credentials in frontend code.
- Do not create fake integrations that appear functional but are not connected.

If an integration is not yet implemented, clearly represent it as unavailable, in development, or awaiting connection.

# 6. THE MOST IMPORTANT PART: A PROPER BUSINESS ONBOARDING EXPERIENCE

The onboarding experience must be one of the strongest parts of Tanat.

A business owner should be able to arrive, understand the platform, register their business, configure an initial AI agent, and reach a successful deployment without needing to understand AI engineering.

Do not dump the user into an empty dashboard immediately after OTP authentication.

Build a guided onboarding journey.

Use a persistent onboarding progress indicator, clear explanations, useful defaults, and the ability to return to previous steps.

## Recommended onboarding flow

### STEP 1 — Welcome to Tanat

After successful OTP authentication, check whether the user already belongs to an existing workspace.

If no workspace exists, start onboarding.

Welcome headline:

**Let's get AI working for your business.**

Supporting text:

"Set up your business, choose what you want AI to handle, and deploy your first agent. Tanat takes care of the infrastructure."

Primary action:
"Set up my business"

Secondary information:
"Already have a workspace? Join an existing workspace."

Do not ask the user for technical configuration at this stage.

### STEP 2 — Business information

Collect:

- Business name.
- Business type / industry.
- Business description.
- Website URL (optional).
- Business email.
- Business country.
- Business timezone.
- Business logo (optional).

The website URL can later be used as a knowledge source, subject to an explicit crawl/import step.

Allow the user to describe their business naturally.

Example:

"We operate a logistics company that provides interstate deliveries and shipment tracking for individuals and businesses."

Use this information to personalise subsequent recommendations.

Create the tenant/workspace with a unique identifier.

Allow a workspace slug or URL where relevant, but do not force users to configure a custom domain just to register a tenant.

A business tenant is the organisation identity, not its domain name.

### STEP 3 — What do you want AI to do?

This step is critical.

Do not assume the business wants to sell products.

Ask:

**What would you like AI to handle in your business?**

Allow multiple selections.

Organise options into categories:

CUSTOMER EXPERIENCE
- Customer support.
- Sales and lead qualification.
- Product and service enquiries.
- Order management.
- Appointment and booking management.
- Customer feedback and complaints.

BUSINESS OPERATIONS
- HR and employee support.
- Internal IT support.
- Operations and administration.
- Procurement and supplier enquiries.
- Finance and invoice assistance.
- Reporting and business intelligence.

KNOWLEDGE AND PRODUCTIVITY
- Internal knowledge assistant.
- Document research.
- Data analysis.
- Report generation.
- Team productivity.
- Technical documentation support.

CUSTOM WORKFLOWS
- Custom business automation.
- Custom AI agent.
- Other.

Allow users to select multiple capabilities.

Provide an "I'm not sure yet" option.

Do not force the user to choose an agent category before they understand the possibilities.

### STEP 4 — Recommend agents

Based on the business description, industry, and selected responsibilities, recommend relevant agent templates.

For example:

A logistics company might receive:
- Customer Support Agent.
- Shipment Enquiry Agent.
- Booking Agent.
- Internal Operations Agent.

A SaaS company might receive:
- Technical Support Agent.
- Customer Success Agent.
- Product Knowledge Agent.
- Lead Qualification Agent.

A school might receive:
- Admissions Enquiry Agent.
- Student Support Agent.
- Parent Communication Agent.
- Internal Knowledge Assistant.

A hospital might receive:
- Appointment Assistance Agent.
- General Enquiry Agent.
- Patient Information Agent.

For healthcare and other regulated use cases, clearly distinguish administrative assistance from diagnosis, treatment, or other restricted professional decisions.

A restaurant might receive:
- Customer Enquiry Agent.
- Reservation Agent.
- Menu Information Agent.
- Order Assistance Agent.

Let the user select which recommended agents to provision.

Include the option to create a custom agent.

Do not automatically activate every recommendation.

### STEP 5 — Configure the first agent

Provide a guided agent setup screen.

Collect:

- Agent name.
- Agent purpose.
- Description.
- Communication tone.
- Responsibilities.
- Things the agent must not do.
- Escalation destination or process.

Provide editable defaults based on the selected template.

For example, a Customer Support Agent should receive a sensible initial configuration.

The user should be able to customise its instructions without having to write a complicated system prompt.

Include a simple preview of how the agent will behave.

### STEP 6 — Add business knowledge

An agent must understand the business before it can provide reliable answers.

Provide several knowledge ingestion methods:

- Add website URL.
- Upload documents.
- Upload PDFs.
- Upload FAQs.
- Add text manually.
- Add product or service information.
- Import approved business data.
- Connect supported business systems.

Explain why knowledge matters.

Suggested text:

"Give your agent the information it needs to represent your business accurately."

Allow the user to skip this step, but clearly explain that the agent may have limited business-specific knowledge until sources are added.

Knowledge sources should be reusable across agents, with access controls determining which agents can retrieve them.

Do not expose another tenant's knowledge under any circumstances.

### STEP 7 — Choose where the agent should work

Ask:

**Where should your AI agent be available?**

Organise choices into three groups.

CUSTOMER COMMUNICATION
- Website chat widget.
- WhatsApp.
- Telegram.
- Email.
- Other supported channels.

TEAM COMMUNICATION
- Slack.
- Microsoft Teams.
- Other supported internal channels.

BUSINESS APPLICATIONS
- Shopify.
- CRM.
- Calendar.
- Inventory.
- Other supported integrations.

Show which integrations are available, which require authorisation, and which are coming soon.

The user should be able to configure multiple deployments for the same agent.

If a user chooses website deployment, show the appropriate setup instructions.

If a user chooses WhatsApp, guide them through the actual supported connection flow.

Never display a successful connection state unless the connection has been verified.

### STEP 8 — Permissions and actions

Before deploying an agent, explain what it can and cannot do.

For example:

A customer support agent may:
- Read approved FAQs.
- Check order status.
- Create a support ticket.

It should not automatically:
- Refund a customer.
- Change account ownership.
- Transfer money.
- Access unrelated customer records.

Use permission controls for actions that change external systems.

Support:
- Read-only permissions.
- Action permissions.
- Human approval requirements.
- Restricted actions.
- Escalation rules.

Sensitive financial, account, and irreversible operations should require explicit permission and appropriate approval policies.

### STEP 9 — Test your agent

Provide an interactive testing environment.

The user should be able to ask questions as though they are a real customer or employee.

Display:
- Agent response.
- Sources used, where appropriate.
- Tool actions taken.
- Errors.
- Escalation behaviour.
- Permission restrictions.

Allow the user to edit configuration and retest.

Make the testing environment feel like a real conversation rather than a technical debugging console.

### STEP 10 — Deploy

Show a deployment summary:

- Agent name.
- Business workspace.
- Connected knowledge sources.
- Enabled capabilities.
- Configured permissions.
- Selected channels.
- Deployment readiness.

Primary action:

**Deploy agent**

Once successfully deployed, display a clear success screen.

For website deployments, provide:
- Installation instructions.
- Copyable embed code where supported.
- Widget preview.
- Installation status.
- Domain configuration where required.

For other channels, display their actual connection status and next steps.

### STEP 11 — Enter the workspace

After deployment, take the user to a populated dashboard that shows their actual setup.

Do not leave users with an empty, confusing dashboard.

# 13. PRODUCT UX PRINCIPLES

Follow these principles throughout the platform.

### Business-first, technical depth when needed

A nontechnical business owner should be able to provision an agent without writing code.

A developer should be able to access deeper configuration and integration capabilities.

### Progressive disclosure

Do not show every advanced setting during onboarding.

Start with the minimum information required to create a useful agent.

Make advanced configuration accessible later.

### No dead ends

Every empty state should explain:
- What this area does.
- Why the user might need it.
- What they should do next.

### Clear status

Always communicate whether something is:
- Connected.
- Disconnected.
- Processing.
- Failed.
- Awaiting approval.
- Draft.
- Published.
- Paused.

### Realistic feedback

Never show fake success messages.

If an operation fails, explain what happened and how to resolve it.

### Responsive design

Design for desktop, tablet, and mobile.

Do not simply shrink the desktop interface.

### Accessibility

Use proper contrast, keyboard navigation, semantic structure, visible focus states, and accessible form controls.

### Empty, loading, and error states

Design all three for every important workflow.

# 14. SECURITY, MULTI-TENANCY AND AGENT GOVERNANCE

This is infrastructure software, so security cannot be an afterthought.

Inspect and implement appropriate protections for:

- Tenant data isolation.
- User authentication.
- Workspace membership.
- Role-based access control.
- Secure API keys.
- Integration credentials.
- Knowledge access.
- Agent tool permissions.
- Conversation access.
- Audit logs.
- Rate limits.
- Usage limits.
- Execution timeouts.
- Human approvals.

Agents should operate with least-privilege access.

A Customer Support Agent should not automatically gain access to financial operations because both agents belong to the same tenant.

Sensitive actions should have explicit permissions and, where appropriate, human approval.

Ensure that one tenant cannot access another tenant's:
- Knowledge.
- Conversations.
- Agents.
- Credentials.
- Usage data.
- Deployments.
- Logs.

Do not rely on frontend restrictions for security. Enforce permissions on the backend.
